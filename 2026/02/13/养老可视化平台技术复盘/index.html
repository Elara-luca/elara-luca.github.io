养老可视化平台技术复盘

作者: Elara
发表于2026-02-13
更新于2026-03-23
项目

一、项目背景

随着中国老龄化进程加速，养老院选择成为许多家庭的痛点。信息碎片化、筛选效率低、决策困难是用户面临的主要问题。

基于这个痛点，我设计并实现了一个养老院智能筛选与可视化平台，帮助用户通过多维度问卷获得个性化推荐，并通过可视化图表对比不同区域的养老院数据。

项目目标：

  • 提升用户筛选效率（从翻阅多个平台到一站式决策）
  • 提供可解释的个性化推荐（告诉用户为什么推荐这家）
  • 探索LLM在垂直领域的落地方式（防止幻觉、保证准确性）

二、技术架构

技术栈：

  • 后端：Spring Boot + MyBatis + MySQL + Redis
  • 前端：Vue + ECharts
  • AI：LLM API（意图解析 + 文案生成）

三、核心设计一：数据建模与性能优化

3.1 分表设计

在设计数据库时，我分析了数据的特点：

表类型 数据内容 读写特点
基础信息表 名称、地址、联系方式 读多写少，基本不修改
动态信息表 床位空余、入住率 频繁更新（每小时）
统计信息表 平均评分、评论数 定期更新（每天）

基于这个分析，我把三类数据拆分成三类表。收益有三点：

  1. 减少锁竞争：频繁更新的动态信息表独立，不会阻塞对基础信息的查询
  2. 提高缓存命中率：静态信息可以放心做Redis缓存，不用担心频繁失效
  3. 便于扩展：未来如果动态信息写入压力大，可以单独对这个表做分库分表

3.2 逻辑外键 vs 物理外键

我没有使用数据库的物理外键（FOREIGN KEY），而是采用逻辑外键，通过应用层代码维护表间引用关系。

  • 性能：物理外键在INSERT、UPDATE时会检查关联表，产生锁竞争。特别是动态信息表写入频繁，如果用物理外键，每次更新都要锁基础信息表
  • 扩展性：未来如果对动态信息表做分表，物理外键无法跨分片维护
  • 软删除兼容：我用了逻辑删除（deleted字段），物理外键会干扰软删除逻辑

代价是：数据一致性需要自己在代码里保证。我的做法是：

  • 用@Transactional事务保证多表更新的原子性
  • 关键业务逻辑加分布式锁

3.3 索引优化

针对高频查询场景，字段建立了联合索引。查询从全表扫描优化为索引扫描。
eg：联合索引：INDEX idx_area_price (area, price_level)

四、核心设计二：个性化推荐引擎

推荐系统的核心挑战是准确性和可解释性的平衡。我没有选择复杂的机器学习模型，而是用加权评分模型。

4.1 两阶段策略

  1. 硬筛选：先用SQL做精确过滤（地区、价格区间），剔除不符合基本条件的养老院
  2. 软排序：在筛选后的结果集上做加权排序

4.2 画像构建：

用户标签从问卷答案提取标签
用户填写问卷后，系统会从答案中提取出用户标签。
养老院画像：从服务+设施提取标签

养老院的标签来源有两个：

来源 说明 示例
服务项目 养老院提供的护理服务类型 medical（医疗服务）、rehab（康复训练）
设施配置 JSON格式存储的设施列表 barrier_free（无障碍）、gym（健身房）

匹配分数计算公式：
最终分数 = 标签匹配分 × 0.8 + 基础分 × 0.2

4.3 兜底机制

如果筛选后结果少于3家，系统会自动放宽筛选条件（价位范围扩大20%），确保用户不会看到空结果。

五、核心设计三：LLM智能推荐

LLM最大的问题是幻觉，它可能编造不存在的养老院或捏造评价。我的设计原则是：LLM只做自然语言理解和文本生成，不做事实判断。

5.1 架构设计

  1. 用户输入：“我想找杭州西湖区，护理条件好，最好有中医服务的养老院”
  2. 意图解析（NLU）：通过Prompt Engineering让LLM输出结构化JSON
  3. 数据库检索：用提取的条件生成SQL，查询真实数据
  4. 文案生成（NLG）：将查到的养老院数据发给LLM，生成个性化推荐语

5.2 容错与降级

  • 解析准确率约85%，失败时降级为手动筛选页面
  • 关键字段（如地区）如果LLM提取不准，用模糊匹配在数据库里再查一遍
  • 每次推荐调用2次LLM API（解析+生成），单次成本约0.02元
  • 相同问题用Redis缓存，缓存命中率约40%

6.2 防重复提交

用Redis分布式锁，以userId + 业务ID作为key，设置5秒过期时间，防止用户重复提交。

6.3 软删除

采用逻辑删除（deleted字段），配合MyBatis-Plus的@TableLogic，数据可恢复，不影响统计。

6.4 事务一致性

多表更新用@Transactional(rollbackFor = Exception.class)保证原子性。

八、总结

项目收获：

  • 积累了数据库设计（分表、逻辑外键、索引优化）的实战经验
  • 探索了LLM在垂直领域的落地方式，形成了“NLU+检索+NLG”的可复用模式

未来改进方向：

  • 引入ES替代MySQL的复杂查询，提升搜索体验
  • 优化推荐权重，让模型更精准
  • 增加用户反馈机制，形成推荐闭环
