多模态集成TTS/OCR/LLM

作者: Elara
发表于2026-02-13
更新于2026-03-23
实践记录

最近闲着没事，想着把几个常用的 AI 能力集成到应用中。选了三个比较有代表性的：TTS（文字转语音）、OCR（图片文字识别）、LLM（大语言模型）。

用 Spring Boot 当后端框架，把这三个能力封装成接口，方便以后复用。

一、这三个东西到底是啥

TTS（Text-to-Speech）

文字转语音，就是你给一段文字，它给你返回一段音频。常见场景：语音播报、有声读物、智能客服。

OCR（Optical Character Recognition）

图片文字识别，你传一张图，它把图里的文字提取出来。常见场景：身份证识别、发票录入、截图转文字。

以上两个用的都是腾讯的api

LLM（Large Language Model）

大语言模型，就是你问它问题，它给你回答。
这个调用方式有很多种，java也有langchain4j专门调用LLM，上篇博客有说到，本次简单带过一下

二、整体思路

我的设计很简单：

  1. 写三个独立的 Service，分别封装 TTS、OCR、LLM 的调用逻辑
  2. 写一个 Controller，暴露三个接口，分别测试
  3. 把配置文件抽到 application.yml 里，方便换 key

不搞复杂的业务串联，先保证每个功能都能跑通。

LLM 调优

1. System Prompt 要写好

GPT 的 system prompt 对输出质量影响巨大。别光传 user 消息，加一个 system 消息效果翻倍：

2. 控制 temperature

temperature 越低，回答越保守、稳定；越高，越有创意但也容易胡说八道。

  • 问答类：temperature 0.3 - 0.5
  • 创意类：temperature 0.7 - 0.9

3. 处理 token 限制

GPT-3.5 单次最多 4096 token，超出就报错。如果对话太长，可以：

  • 只保留最近几轮对话
  • 用 max_tokens 限制回复长度

五、OCR 结果的后续处理

OCR 识别出来的文字，经常空格、换行乱七八糟，还带一堆没用的话。识别只是第一步，清洗和结构化才是重头戏。

下面是总结的几个处理套路。

1. 先去掉乱七八糟的字符

OCR 经常会识别出莫名其妙的符号，比如把一识别成—，把0识别成O。

2. 提取关键信息（正则）

大部分业务场景关心的只是几个关键字段。用正则表达式直接捞出来。

3. 结构化提取（用 LLM 兜底）

正则表达式能搞定 80% 的情况，但遇到格式千奇百怪的文本可以用 LLM 来提取结构化信息。

  • 正则能搞定的一律用正则，快且免费
  • 正则搞不定的、格式特别乱的，再用 LLM 兜底
  • 可以把两种方式组合，先正则，再让 LLM 补

六、总结

折腾下来最大的感受是：调 API 不难，难的是把效果调好。
每个服务官方给的 demo 都能跑通，但真要拿到实际场景用，就得各种调参数、加预处理。
